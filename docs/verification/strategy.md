# 検証方針

## 基本動作の受入条件

起動、入力、操作の受付、保存、再起動、再開までを検証します。障害時は未処理例外、無期限の待機、重複送信、保存済み状態の後退を失敗とします。生成内容の意味や画質は、この基本動作と別に判定します。有限のテストで任意の環境の無故障を証明するものではありません。

## 対象と配置

```text
tests/
  backend/{unit,integration,structure}/機能/
  frontend/{unit,integration,structure}/機能/
  tools/{unit,integration,structure}/機能/
  scripts/integration/機能/
  bootstrap/integration/機能/
  system/e2e/{package,web}/
```

単体は純粋な判断、結合はDB・ファイル・プロセス・通信境界、構造は依存・参照・契約、E2Eは公開入口から保存・再開までを確認します。共通fixtureは対象内の`support`へ置きます。scriptsの実接続は通常のテスト検出に含めず、実行管理・予算・証跡・後始末のロジックをtestsから検証します。

## 実行する検査

| 操作                                              | 範囲                                    |
| ------------------------------------------------- | --------------------------------------- |
| `pnpm check`                                      | Nxで選んだ関連範囲                      |
| `pnpm check:ci`                                   | 関連範囲とCI用の全Python測定            |
| `pnpm check:all`                                  | 全プロジェクトの静的検査・テスト・build |
| `pnpm build`                                      | 配布物の作成・同梱検査・隔離導入のE2E   |
| `pnpm test:web`                                   | 配布wheelのCLIから起動するブラウザーE2E |
| `pnpm verify:live --allow-real-llm --output PATH` | 許可した実LLMの検証                     |

Pythonの対象はsrc、tools、scripts、bootstrapで、未実行ファイルを含めます。行と分岐の閾値は[pyproject.toml](../../pyproject.toml)を正本にします。実機用の許可や外部トレースの環境変数は通常ゲートから取り除き、テストの通信は自分が開始したloopbackの擬似APIに限定します。実モデルへ切り替えて不足を埋めません。

## E2Eと障害の判定

CLIとブラウザーの両方から、初期化、会話、行動、編集、画像、回収、共有用出力、再起動を検証します。配布wheelにはReactも同梱し、ソース版だけで動く状態を合格にしません。ブラウザーの各テストは別の作業場所とOSが割り当てたポートを使用します。

ページ例外、console.error、想定外のHTTPエラー、失敗した要求はテストの失敗とします。画面の更新でキャンセルされたGETは別の観測として記録し、送信操作の中断や接続失敗と区別します。障害注入はその要求の経路・方式・状態・件数に限定して宣言します。再試行で成功した結果や、既知の未達、skip、探索のcaptureを受入成功へ昇格させません。

応答喪失、重複・並行操作、保存途中停止、破損、設定変更、SSH切断、部分回収、監視停止、ログ取得とGPU停止の失敗を回帰テストで扱います。タイムアウトと中断は通常の失敗と区別して残します。

再開の応答喪失も通常送信と別に検査します。再開前のGETが遅れて届く場合と、再開の受付応答より先にGETで受理を確認する場合を含めます。同じ操作IDの受理回数で順序を判断し、移動一回・追加推論ゼロ・下書き保持・後続操作の監視を確認します。配布wheelと実HTTP APIを使い、モデル境界だけをloopbackの固定応答へ置き換えます。

再開要求がサーバーへ届かない場合と、通信失敗後のGETも失敗する場合を分けます。新しいGETで再開可能な中断を確認してから明示的に再開できること、確認操作だけではPOSTを増やさないことを確認します。

未着後の確認GETを保留したまま次の明示再開を始め、前のGETを後から返す順序も検査します。同じ操作ID・同じ受理予定回数でも、次の要求の待機と照会が継続し、受理前に新規送信を許可しないことを確認します。

画面の高さと文字の拡大を組み合わせ、発言欄の表示だけでなく、余白を除いた履歴領域に実際の本文1行分の高さがあることも確認します。日英と表示密度を含め、履歴内の台詞を読めること、下書きと送信操作を保つことを同時に検査します。

実行全体と個別検査の期限を分けます。準備とビルドの後に始まった検査を、親と同じ期限の流用で途中終了させません。親の期限と個別検査の期限が不整合な設定は実行前に拒否します。タイムアウトでも取得済みの出力をCIへ残し、個別検査の上限を延ばして成功へ変えません。

ブラウザーと並行して状態を確認するテスト用API接続は、各応答で閉じます。待機期限が異なるクライアントとサーバーの間で、期限切れ接続を再利用する競合を避けます。API照会の再試行も無効にし、失敗を隠しません。ブラウザー自身の通信は通常の接続を使います。

## 実LLMとT4

会話の画面E2Eは日英それぞれで履歴のページ境界を越えて送信し、再読込後の全件復元と順序、明示的な末尾への移動、接続失敗時の内容・下書きの保持を確認します。移動と会話は共通の現在地、自然文・明示入力、行動だけの送信、段階ごとの中断と復旧で検証します。スクロールは標準の操作と強制配色を維持し、枠の接触・狭い画面・文字拡大を確認します。

長い実会話は`node tools/runtime/python.mjs -m scripts.acceptance.conversations.long --allow-real-llm --output .artifacts/records/reports/long-conversation/attempt-1`で実行します。上限と入力は[専用設定](../../scripts/acceptance/conversations/long.toml)を正本にします。初期データだけを公開APIで準備し、すべてのターンを配布wheelの画面から送信します。画像生成とGPU確保は行いません。同じ親フォルダーの別出力へ再実行すると、会話、消費、期限を保持します。受付不明・未終端の操作は再送せず確認を要求します。通常のゲートへ実モデルを持ち込みません。

長会話、日英の行動確認、画像用の呼び出しを同じ許可枠で実行するときは、各入口に同じ`--ledger`、`--max-calls`、`--max-seconds`を指定します。最初に公開APIで新しい許可台帳を作成し、既存の作業場所にはその台帳を接続します。再接続で期限や予約数を戻さず、過去の台帳も保持します。

移動後の会話画像だけを検証する場合は、実機入口に`--conversation-id`で同じ作業場所の保存済み会話を指定します。キャラクターと二人の画像を各一枚生成し、既存の画像予約とCU・時間予算を引き継ぎます。保存済み結果の確認は実際のターン数を使い、履歴のページ境界も画面で復元します。

終了後に検証用サーバーを停止し、公開APIで操作の復旧状態と保存件数を再確認します。途中経過の観測を残したまま、`run.json`の`final_state`へ観測日時と最終状態を記録します。再確認に失敗した結果も不合格とし、推論や自動再送で確認を代用しません。

失敗した操作を残したまま再送しません。終端と原因を確認して別の検証会話から始める場合は`--new-conversation`を明示します。元の会話と失敗記録を保持し、同じ台帳の残量と期限で実行します。

保存済みの前半を再利用する場合は`--fork-after-turn 確定ターン数`を指定します。新しい検証会話へ指定位置まで分岐し、以後の発言を画面から送信します。原本を訂正せず、分岐元・位置を記録し、同じ呼び出し上限と期限を適用します。構造の成功とは別に本文と視点を評価し、人物の区別、現在地、条件付きの相談、訂正後の予定、原文を根拠にした記憶を評価します。

問題の場面だけを再検証するときは`--through-turn 終了ターン数`で範囲を絞ります。設定済みの全体ターン数を超えず、予算と期限は増やしません。実モデルと全体検査を同時に動かすとメモリが不足する環境では、実モデルを解放してから全体検査を実行します。

実接続は`scripts/acceptance`で明示許可したときだけ実行します。SDKの書き換えや内部DBへの挿入を行わず、公開APIで会話を作成します。送信前に予約した回数と期限を、再起動や修正後の再検証にも引き継ぎます。

実LLMでは日本語・英語、構造化応答、実モデルのトークン計測、保存後の再起動と重複防止を確認します。`--allow-gpu`を加えた場合は、T4で人物・作品・会話・単発画像、標準画面、回収、所有GPUの終了を確認します。検証が確保していないGPUや外部サーバーを停止しません。接続不能、認証不足、資源不足、終了未確認は合格にしません。

## 証跡とAI解析

対象コミットと内容ハッシュ、環境、操作ID、実行範囲、期待結果との差、失敗段階、コード位置、保存先、終了確認を記録します。診断に例外本文、変数、HTTP本文、資格情報を含めません。生の要求・応答と画像は私有データに保持し、診断から分離します。

診断ログの排他待機は有限とし、書き込み不能を処理の呼び出し元へ戻します。ログ保存の失敗で本来の処理を無制限に待機させません。

検査の起動・終了管理が予期しない例外で失敗した場合も、失敗状態と終了時刻を確定します。例外は種類だけを保存し、本文や変数を転載しません。Pythonの対象選択失敗と環境不足も終端として記録し、記録ファイルを原子的に置き換えます。

AIが修正する場合は、失敗した契約と再現手順から同じ原因の範囲を調べ、原因を修正して関連検査を再実行します。検査の削除、恒久的なskip、広い失敗除外、自動モデル切り替えで受入条件を緩めません。

実機の画面確認だけをやり直す場合は、同じ親フォルダーに新しい`--output`を指定し、`--resume 以前の出力/run.json`を付けます。保存済みの会話と画像を使い、新しい推論や画像要求は送りません。停止済みT4を再度確保する場合も`--allow-gpu`が必要で、残りの累積予算を適用します。

利用者が追加時間を明示許可した場合だけ、再確認に`--extend-gpu-seconds 秒数 --authorization-id UUID`を付けます。元の上限、消費時間、画像予約、CU制限は維持し、許可IDと追加時間を同じ台帳へ追記します。同じ許可IDは一度だけ適用します。実LLMの回数・期限は延長しません。

長会話の実機検証は`python -m scripts.acceptance.conversations.long --llm-profile PROFILE`で接続プロファイルを指定できます。使用するモデルは作業設定の接続プロファイルで定義します。未指定時は会話入力の既定値を使い、再開時に既存の会話を別のプロファイルへ自動変更しません。実行には別途明示許可と既存使用分を保持する台帳が必要です。

集合予定の短い実機ケースは `--case meeting-ja` と `--case meeting-en` で指定します。ケースごとに別の親出力フォルダーを使い、長会話で作った同じ許可台帳を接続します。予定の決定・照会があるターンは保存値を再読み込み前後の画面表示と照合します。それ以外のターンでは予定の表示がないことを確認します。移動と質問を含むターンは台詞の有無を検査し、質問に対応しているかは本文で判定します。

保存済みターン数が指定した終了ターン数と一致する長会話は、自動で読取専用の再検査になります。同じ親フォルダーに新しい出力先と既存台帳を指定します。保存済みと新規のターンへ同じ確認項目を適用し、元の会話と失敗を変更しません。台帳の期限後も保存済みの確認は実行できますが、追加送信は禁止します。保存済み件数が不足する場合は読取専用とせず、通常どおり呼び出し残量と期限を適用します。
