# 複数題材の継続検証

## 準備

[検証設定](../../tests/fixtures/story-validation/config.toml)と原文を実行前に固定する。[計画補助](../../tests/live/story_suite.py)は対応するFakeを構造検証へ使い、実測では明示したローカルLLMだけを呼ぶ。`--llm-profile`で計画用4B・9Bを選ぶ。呼び出し数は構造修正を含め送信前に加算する。

計画の構造成功と原文一致を分けて記録する。[確定処理](../../tests/live/story_validation.py)は実LLMの保存済み計画、原文と計画のハッシュ、AIの採否を確認して画像要求へ変換する。未承認の題材をFakeへ置き換えて最終検証に含めない。

## 予算と再開

[累積台帳](../../tests/live/verification_budget.py)は旧台帳のハッシュ・既使用CU・保存枚数を引き継ぐ。開始時の口座が同一で割当0であることを確認し、旧観測以後の帰属不明な残高減少も保守的に差し引く。旧台帳は変更しない。新しい実行の基準残高は一度だけ保存する。

各確保区間の開始、所有ID、停止時刻、所有解放を記録する。停止未確認の区間は計測を継続し、別GPUを起動しない。確保前に残りの累積時間から現在の送信・停止期限を決め、独立監視へ渡す。ローカル調査中の時間とGPUの所有時間を混同しない。

要求は画面への書出し・API送信前に予約する。受付不明は予算へ残し、実行IDで照合する。保存・選択・未評価・品質合否を独立して集計する。空のモデル・seedの組合せを作品として数えない。

## 出力と障害

PNGとPDFは1〜8場面を4枠ずつ組版する。pypdfで全ページの読取り、ページ数、寸法、内容と画像を検査し、実成果物はPopplerで再描画して画像配置と本文順序を確認する。必要画像が欠けた場合は仮画像を作らない。

隔離wheel受入の失敗は、削除前の一時領域から初発失敗と直近イベント、操作ID、実行IDを許可した項目だけで保存する。保存先は品質ゲートの検証領域へ分離する。例外本文、要求本文、認証情報は記録しない。診断保存の失敗と終了処理の失敗で元の失敗を置き換えない。

変更中は累積L2、固定した最終内容は累積L3とWindows・UbuntuのCIを実行する。結果は[検証記録](results/story-stability.md)に記載し、未実施と不合格を区別する。
