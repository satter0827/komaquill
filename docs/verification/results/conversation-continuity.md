# 会話の継続・表示と実LLMの確認

## 対象と確認範囲

確認日は2026年11月6日（JST）。基準コミットは`6a349f0863187dfb64217f1bcfc02869330b53e0`です。変更中の対象は各実行の入力SHA256で識別します。Windows ARM64上のPython 3.12.15、Node 24.15.0、LM Studioの`qwen3.5-4b-uncensored-hauhaucs-aggressive`で確認しました。各自動検査の対象版と成否は`checks.json`とCIの記録を正本とします。

目的は、発言が黙って失われず、通信失敗後も表示済みの履歴と下書きを保持し、長い会話を画面から送信・再読込できることです。任意の生成文の意味や自然さの保証とは分けて判定します。

## 原因と修正

| 対象 | 原因と観測 | 修正 |
|---|---|---|
| 発言の欠落 | 相手が別の場所にいると、生成済みの発言と動作を複数の層で削除していた | 同行・残留を必須の応答項目にし、所在との矛盾を検証する。原応答を保持し、修正上限で失敗する。本文の黙示的な削除を廃止 |
| 状態だけの空返答 | 同席中でも内部状態の変更や確定行動があると、本文のない返答を完了扱いにできた | LLMと保存で同じ可視出力の検証を共有。新しい描写も発言も動作もない返答を拒否し、有効な無言の描写と区別 |
| 履歴の消失 | 再取得の失敗で取得済みの画面全体をエラーへ置き換える | 履歴と下書きを保持して再取得を案内する。会話、人物、作品、旧会話へ適用し、最新状態が必要な更新を停止 |
| 別行動の案内 | 案内が履歴の上端にあり、入力時には見えない | 入力欄のそばに相手の場所と合流操作を表示。行動を送信するまで現在地を変更しない |
| 枠線とスクロール | 行動の負の余白と、背景に合わない標準スクロールの表示 | 負の余白を削除し、標準の細いスクロールへ配色する。強制配色時はOSの表示へ戻す |
| 起動直後の接続 | APIが準備される前に開発画面を起動していた | 今回の起動の接続記録とAPI応答を確認してからViteを起動 |
| 接続切断時の例外 | WindowsのProactorでソケットの後始末が中断する | HTTPと実機確認で標準SelectorEventLoopを共有。詳細は[設計判断](../../decisions/0022-reliability-and-storage.md)を参照 |
| 描写の視点と動作 | 別行動時の相手側の描写、過去の移動を相手の動作へ写す応答を実モデルで検出 | 描写の観測位置を明示し、確定行動の直近入力にも両者の現在地を付ける。状態と本文を別に評価 |
| 相談と行動案の分類 | 将来の行動を広く行動案とする指示が、現在の状態変更に限定する指示と両立していなかった | 今すぐの明示的な状態変更を基準とし、条件付きの準備の相談を会話として扱う。生成する意図の説明も同じ基準へ統一 |
| 検証記録の確定 | 入力変更時は終了コードだけ失敗になり、台帳の喪失時は記録が実行中で残る | 入力変更を成功と区別し、台帳取得と終了処理の失敗も本文を除いて記録する |

開始時には開発APIと画面が停止しており、保存されたPIDは別のプロセスに再利用されていました。元の停止原因は確認できていません。自分が起動したViteを終了する検査では、開発APIも終了し、残留しないことを確認しました。

保存時に空になった過去の発言は、現在の位置関係から推測して復元していません。保存済みの本文と不変の原応答は保持します。

## 自動検査と残る確認

通常ゲートは実モデルを使いません。日英32ターンの画面送信、履歴のページ境界、全件の順序、再読込、通信失敗時の下書き保持と再取得、合流操作、枠線の間隔をE2Eで検証します。矛盾応答の修正成功・上限到達、矛盾する保存済み応答の隔離、分岐と予算の保全、接続切断後の応答と終了も回帰対象です。

初回の全体検査には未使用importがあり、実モデルとの並行実行で空きメモリが約600MBとなったため中断しました。失敗と中断を保持し、importの修正とモデルの解放後に全体検査を再実行します。局所検査や中断した検査を全体の成功として扱いません。

再レビューで同席時の空返答と検証記録の不足を7件再現しました。修正後の関連203件は成功しています。この修正前に完了したPython全件検査は1,291件成功・2件skip、行91.90%・分岐80.66%でしたが、画面検査は修正を優先して中断しており、最終版の全体成功とは扱いません。

長会話を追加した画面検査は、41ケースまで約10分を要しました。既存全件と追加ケースの実測合計が以前の全体期限に近づくため、[画面検査設定](../../../tools/testing/web/config.mjs)で全体の上限へ余裕を設けました。個別ケースの上限、再試行なし、単一worker、失敗検出は維持します。

修正後のローカル全体検査は、入力SHA256 `5083425efada662aa6a5bfbdc125c975a6ee9eba184bc4f0c911cf2206c338be`で21タスクすべて成功しました。Pythonは1,300件成功・OS条件2件skip、行91.93%・分岐80.73%、Reactは71件成功、画面E2Eは63件成功です。実行中の入力変更はありません。画面全件は約15分を要し、旧全体期限には余裕がないことも確認しました。

この後、実LLM用のブラウザー実行コードを擬似APIで直接動かすE2Eを追加し、成功と意図した順序不一致の失敗を確認しました。診断へ例外本文や入力配列を出力せず、種類と識別用ハッシュを保存します。擬似APIの結果を実LLMと表示しないよう入力契約も明示しています。追加の1件と関連Python 26件は成功し、最新の全件判定はPRのCIで行います。

実行コードを使うE2Eからscriptsへの依存をNxにも宣言し、実効グラフで構造検査します。scriptsだけの変更でも、このブラウザー検査が選択されることを確認しました。

最終修正後の実LLM20ターン全件の再実行について、追加の明示許可を受領しました。元の消費と期限を変更せず、別の台帳で新規の検証会話を使います。追加枠の最初の9ターンでは、単独移動・合流・同行と表示順序を確認しました。20ターンへ継続した際、15ターン目の条件付きの相談を自分の意図の更新案へ分類し、E2Eは不合格となりました。累積16呼び出しと元の結果を保持し、指示を修正して14ターン目から再検証します。

生成文には不自然な敬語、末尾の不要な記号、未指定の情景を補う傾向もあり、構造・基本操作の成功を意味品質全般の保証としません。末尾の記号は正しいJSONの文字列内に含まれており、解析による補正ではないことを確認しました。本文を黙って整形・削除していません。

追加枠のattempt-4は20ターンの画面操作には成功しましたが、時刻だけを訂正した予定の曜日が土曜日から日曜日に変わり、内容面では不合格としました。履歴がすべてuser役割のJSONへまとめられていたため、LangChainの標準メッセージで発言者を分離し、計数にも同じ役割を使用するよう修正しました。利用者が明示した事実を相手の生成文で上書きしない指示を加え、検証入力にも変更していない曜日の確認を明示しました。元の22呼び出しと結果は保持します。
