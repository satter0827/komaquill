# 同行する会話の停止・復旧を再検査する

確認日: 2026-11-06（日本時間）。対象はREQ-CONVERSATION-CONTINUITY、REQ-WEB-APP、REQ-HTTP-API、REQ-REAL-ACCEPTANCE。

実装の基準は1bb775c14513d3ed50f03f399bdbaa879214c5fc、入力ハッシュはe01069fd0ff3551cd71502efcf511ad909b8ff6a6082d10c060197c60e35f17c。この記録の追加後も同じ製品コードを使う。全件検査の対象コミット、内容ハッシュ、範囲、結果は私有の.artifacts/records/reports/checksと[PRのquality・security](https://github.com/satter0827/komaquill/pull/49/checks)へ対応させる。

## 要件と確認範囲

主人公と相手が同行し、移動と会話を一度の送信で保存できることを基準にした。保存後の表示、停止後の復旧、操作の重複防止、通信不能からの確認操作、検証生成物の保持も対象とした。機械検査の成功と、モデルの意味の正確さ・実画像の品質は分けて判定する。

公開API、短い保存トランザクション、チェックポイント、Queryキャッシュ、送信・再開操作、入力保持、検証コード、原要求・原応答を照合した。通常送信の応答喪失だけでなく、明示した再開の前後を別の障害境界として確認した。

## 発見した問題と修正

| 問題                                         | 原因                                                                                                             | 修正と回帰条件                                                                                                                      |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 再開が受理されても古い中断状態が画面に残る   | 同じ操作IDの終端状態を保護するだけでは、再開前後の観測を区別できない。再開の応答喪失時も監視を開始していなかった | 受理した再開回数を保存し、回数とその回数内の終端状態で観測を統合する。再開の送信前から同じIDをGETで確認する                         |
| 遅れた再開応答で後続操作の監視や下書きを失う | 受付応答だけで監視対象と待機状態を更新すると、GETで確認した後の操作へ古い応答が介入する                          | 受理確認をQuery購読へ揃え、対応する要求の待機だけを解除する。古い受付応答で監視対象を戻さない                                       |
| 完了済みの操作を再確認すると待機が残る       | 完了済みの確認では再開回数が増えないが、画面が次の回数だけを待つ                                                 | 完了済みの結果と、新しく受理した結果を区別して確認する。完了済みの再確認と重複拒否では回数を増やさない                              |
| 応答がない接続で要求が終了しない             | ブラウザーAPI要求に明示的な通信期限がなかった                                                                    | 生成クライアントの標準フックとAbortSignalで期限を設定し、利用者のキャンセルも維持する。同期処理を含む更新と読み取りの待機枠は分ける |

再開回数は同じ短いトランザクションで更新する。操作ID、受付入力、確定済みの移動、過去の本文、行動、履歴ハッシュ、LLM通信は変更しない。通信期限から生成失敗を推測せず、受付不明の更新要求を自動再送しない。新しい汎用実行基盤や保存方式は追加していない。

同じ原因を確認するため、個別操作と操作一覧、画像・作成処理の終端保持、通常送信と明示再開も調べた。再開回数の順序付けは明示再開を持つ会話操作へ限定し、再開しない生成処理の終端保護は維持する。

## 修正過程の検証

- 修正前の回帰テストは、再開後も中断状態のままであることを検出して失敗した。失敗ログを保持した。
- 保存・会話・HTTPの関連206テストが成功した。受理回数の増加、重複拒否、失敗段階の解除、再中断後の再開、再起動後の回数、保存済み応答の再利用を含む。
- 画面・通信・Queryの関連44テストが成功した。古い回数の応答、終端状態、受付応答より先のGET、後続操作への遅れた応答、完了済みの再確認を含む。
- 配布wheelと実HTTP APIの復旧E2E6件が成功した。新しい再開ケースは、保存済み応答を使って移動1回・保存1ターン・再開POST1回・追加推論0回を確認した。下書きと次の送信も維持する。
- 通信の回帰は、読取期限、更新期限、呼び出し元のキャンセル、送信本文の保持、自動再送なしを確認する。formatter、lint、型、契約、文書参照も確認した。

これらは修正過程の部分検証である。全体成功は最終対象版の全件検査と配布物の検査で判定する。各実行の対象と期待結果との差は私有のzero-review-*.logとwebの個別証跡へ保持する。

## 保存済みの実会話と未完了の受入

保存済みの実4B会話20ターンを、期限後も追加送信できない読取専用で再検査した。本文、件数、順序、再読込を通過し、許可台帳の使用回数は変わらなかった。最終版の配布物でも同じ確認を行い、結果を新しい出力先へ保存する。これは現在版で実モデルの20ターンを新規生成した結果ではない。

過去の最終原要求も再調査した。40メッセージ・実測5,264入力トークンの中に、元の集合場所、訂正時刻、条件付き提案と、利用者の発言を優先する指示が含まれていた。4Bが準備状況や集合場所を補った問題を、入力欠落や保存破損とは判断しない。原文を検索置換する後処理や、成功するまでの自動再生成は追加していない。

追加の実推論は行っていない。以前の許可台帳は期限切れであり、使用量と期限を戻していない。T4は既存の累積CU上限と予備を維持すると起動条件を満たさず、新規確保していない。4Bの要約の意味の忠実さ、T4の追加2画像・標準画面・回収・終了、物理端末のIMEとソフトウェアキーボードは未完了として保持する。
