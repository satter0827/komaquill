# 検証手順

## 対応環境

開発環境はWindows x64またはARM64とPowerShell 7です。ARM64ではx64 Pythonを使用します。CIはWindowsとLinuxで実行します。Colabの検証GPUはT4、既定モデルはPony Diffusion V6 XLです。Python、ComfyUI、フロントエンド、公式Colab CLIとGPU依存はパッケージ内の固定値と依存ロックに従います。

外部ComfyUIには標準APIと、使用するモデル・標準ノードが必要です。モデル準備と素材保全にはKomaquillの画面拡張も必要です。

## GPUを使わない品質検査

開発環境を有効にして実行します。

```powershell
python scripts/check.py --level 2
```

選択したレベルの検査が終了コード0で完了することを確認します。既定はL2です。レベルは累積し、L3にはL1・L2のすべてを含みます。GPU確保や有料API呼び出しは行いません。

| レベル | 検査範囲 |
|---|---|
| L1：Static | 整形、lint、strict mypy、依存方向・循環参照、文書参照、作業ツリーの秘密情報・生成物混入 |
| L2：Test | L1に加え、Python・JavaScript・PowerShell検査、依存ロック照合、カバレッジ、実プロセスでのCLI基本操作 |
| L3：Full | L2に加え、隔離build、配布物検査、隔離wheelでのCLI基本操作、取得済みGit履歴全体の秘密情報 |

公開前とWindows／LinuxのCIはL3を実行します。`--plan --json`で検査ID、順序、前提と出力先を確認できます。`--check 検査ID`は前提工程を含む個別検査であり、全体成功として登録しません。

| 対象 | 確認内容 |
|---|---|
| Python | Ruffの整形・lint、strict mypy、依存方向と循環参照 |
| 生成と回収 | 送信前記録、受付不明の照合、部分保存、破損履歴、並行回収、重複防止 |
| 監視 | 親プロセス終了後の継続、二重起動、PID再利用、設定固定、起動中の停止 |
| 終了 | 通常・強制終了、切断後の復旧、ログ取得・GPU終了・後始末の個別結果、所有記録の保持 |
| モデル | 固定取得元とSHA256、同名別モデルのノード別対応、容量不足、取消、部分取得の再開、ローカル限定モデルの転送 |
| 素材 | 画像・マスク・Saveの観測、上書き前の版の保持、生成入力の固定、保存時の入力版の復元 |
| Windowsの保存 | 読み取り中の実ファイルとの共有競合、短時間の再試行、恒久的な失敗時の既存ファイル保持 |
| 画面拡張 | Node標準テストによる準備・取消・モデル参照の更新、配信ファイルと文言の同梱 |
| 評価 | 人・AIの識別、生成・画像参照、採否・選好、訂正の追記、JSONの一括登録・分析用出力 |
| 配布 | wheelとsdistの内容、隔離wheel環境での初期化・起動・生成・回収・停止、GPU転送物の展開とimport |
| 秘密情報 | Git履歴、追跡ファイル、設定、配布物への混入防止 |

カバレッジは未実行ファイルも含むsrc・scripts・bootstrapのPythonを対象にし、testsを除外します。行90%以上と分岐80%以上を別々に判定します。

結果は`.artifacts/records/reports/quality/実行ID/`へ保存します。`gate.json`に対象版、入力ハッシュ、工程ごとの開始・終了時刻、終了コード、失敗種別と未実行理由を記録します。失敗した工程の依存先を省略しても、独立した秘密情報検査は続けます。

`latest-attempt-lN.json`はレベルごとの最新実行、`latest-success-lN.json`はそのレベル全体の最新成功です。検査中に対象が変わった結果や個別検査は最新成功へ昇格させません。`--level N --status --json`で現在の入力との一致を確認できます。成功記録が存在しても、入力が変わっていれば現在の成功とは扱いません。

## T4と標準画面の検証

GPUを消費するため、品質ゲートとは分けて実施します。Google認証は起動端末で行います。作品・モデル・履歴を変更する前には、GPU停止、保存ファイルの一覧、SHA256を確認してください。

1. startで起動し、準備段階が進んで画面を開かずに端末へ戻ることを確認します。openまたはstart --openによる明示的な画面表示も確認します。起動コマンドの終了後もstatusが監視・GPU・接続を確認できることを確かめます。
2. CLI、App Mode、Node Graphから生成します。画像、実行グラフ、生成条件、実際のモデル・入力ハッシュ、画像の寸法とSHA256を照合します。
3. 不足モデルのある標準ワークフローを開きます。名前・容量・公開取得元・再利用対象を確認して準備します。確認前に取得が始まらず、準備後に不足表示が解消することを確かめます。
4. 標準の画像・マスクのアップロードとSaveを行い、同名の上書き前後を保存します。新しいランタイムで、保存時の入力版を参照するワークフローが復元されることを確かめます。
5. 監視とSSHを失った状態からstartで同じ所有GPUへ復旧します。モデルの全読み直しやGPUの追加確保がないことを確認します。
6. 通常終了で生成と保存を待つこと、強制終了で残った要求を回収不能として記録することを確認します。最終ログ、所有GPUの終了、監視・SSH・待ち受けの終了、再停止での追加確保がないことを確かめます。

再利用する検証コードはtests/liveに置きます。KOMAQUILL_LIVE=1とKOMAQUILL_PROJECT_DIRで対象を明示します。終了試験はKOMAQUILL_LIVE_STOPをnormalまたはrecovery-forceに設定して選択します。後者は検証対象の監視とSSHを中断してから所有GPUを停止します。業務中のセッションへ実行しないでください。

## ログと保存の確認

logs/ランタイムID/capture.jsonで、ログごとの取得結果と最終成功日時を確認します。shutdown.jsonは画像回収、素材保全、ログ、GPU、接続、履歴確定の結果を分けて記録します。失敗しても保存済みログを置き換えません。起動時と終了時の両方に問題がある場合は、元のエラーを表示し、終了側の結果をshutdown.jsonへ残します。

標準の画面拡張は.jsとして配信し、ComfyUIのキャッシュ抑制を使用します。GPU転送物に含むコードを、実際のComfyUI子プロセスの作業フォルダーからimportできることも確認します。

## 制約

新しいColabではモデルを取得し直します。同じランタイムへの再接続では準備済みモデルを再利用します。取得時間は配布元・ネットワーク・割当先に依存します。

認証が必要なモデル、取得元を確定できないモデル、追加ノード、動画・音声は自動導入しません。未保存の画面編集と拡張ノード独自のファイルは保全対象外です。PCの電源断やログアウト後のGPU終了は保証しません。

別のGPUサービスでの拡張利用は標準APIを境界とします。実際のGPU検証はColab T4で行い、他サービスの認証・割当・運用条件は個別に確認します。


## ストーリーの受入

日常ゲートではFakeListLLMと擬似ComfyUIで1・4・8枚、順次保存、部分失敗、二重実行、中断、再開、別条件での再生成を検査します。LLMアダプターの検査はlocalhostの擬似APIだけを使います。外部トレースの環境変数が有効でも送信しないこと、任意のキーや許可変数があっても日常ゲートから実モデルを呼ばないことを確認します。

実4Bの確認はKOMAQUILL_REAL_LLM=1、KOMAQUILL_PROJECT_DIRを明示し、tests/live/test_story.py::test_real_4b_story_planを実行します。この入口はCLIへ--allow-real-llmを渡し、1・4・8場面の計画を作ります。原文の出来事と結末、補足の区別は保存済みの計画を読んで確認します。

4場面の保存済み計画を用意してからT4を1セッション起動します。stories renderで生成し、全場面の完了前に最初の画像と本文を確認できることを確かめます。KOMAQUILL_STORY_RENDERに試行IDを指定したtests/live/test_story.py::test_real_story_saved_imagesで対応と実ファイルのハッシュを照合します。通常終了後にGPU・監視・SSH・待ち受けの終了を確認します。実機用の環境変数を日常の端末へ残さないでください。
