# 複数題材の検証と可視状態の分離

## 背景

一つの短編に固定した描画指示を使う完走検査では、原文からの計画と画像入力の変換を評価できない。Kleinは全体の条件文で生成するが、旧来の二対象上限が計画・単画像・場面設定・固定入力へ分散していた。

実測では、発見前の鍵を机上へ置く計画、閉じた鞄内の本を描画対象へ残す計画、人物のいない物語へ観察者を加える計画を確認した。形式の検査と意味の評価を区別する必要がある。

## 決定

題材と採点条件を先に固定し、Fakeで構造、実LLMで原文の保持、実画像で描画結果を確認する。通常検査は既存のpytest・Pydantic・FakeListLLM、組版はPillowを使う。実測補助は公開APIを呼び、独自の生成経路や汎用エージェント基盤を作らない。

可視対象の一律上限を撤去する。原文に必要な対象を保ち、一瞬を簡潔に描く方針を計画へ渡す。小物の状態には可視性を明示し、不可視の小物を画像入力へ合成しない。元の計画と状態を残すため、生成済みの条件を書き換えない。可視性が正しく宣言されても原文に忠実とは限らず、意味の評価を必要とする。

合格した実LLM計画だけを生成へ渡す。拒否された計画は保存し、共通修正後の新しい計画ではAIレビュー理由を既存の描画方針へ加えて再検証できる。原文と採点条件は変更せず、初回とレビュー後の成績を分ける。実モデルの失敗をFakeの成功で置き換えない。

題材ごとの記録を分け、GPU・モデル置き場・予算は共用する。開始時の設定と使用済み予算を保存し、受付不明や予約だけ残った要求を自動再送しない。通信中は共通の状態ロックを保持せず、終了結果の確定前に再読込みして予算の後退を防ぐ。

## 影響と制約

単画像入力とストーリー入力は同じ対象数の契約を使う。新規計画は小物の可視性を必要とし、同梱のFake応答も更新する。保存済み記録の読取りと新規計画の検査は分ける。

保存・選択・組版の成功は画質合格ではない。小規模な単一seedの実測は一般的な安定性の証明にしない。合格計画がなければGPUを確保せず、原因調査を続ける。解決済みの検証データは要約後に整理し、未解決の問題は最小の証拠を保持する。

運用と検証設定は[検証手順](../verification/story-completion.md)、対象版ごとの結果は[検証記録](../verification/README.md)を参照する。
