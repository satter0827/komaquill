# 複数題材の未達解消

## 対象と受入条件

Klein 4BとWAIの共通工程、実LLMによる8題材の意味、確認用4題材と2seedの作品を確認する。画像用Klein 9Bと二段階生成は対象外とする。実装、保存、画質、原因解決を別々に判定し、判断不能を合格にしない。

予算の正本は[検証設定](../../tests/fixtures/story-validation/config.toml)。前回の保存画像とCU使用を引き継ぐ。T4の確保回数を承認条件にせず、停止と所有解放、原因への対処、残予算を確認して明示的に起動する。受付不明の要求は再送しない。

## 修正と実施順序

1. 旧台帳を保持し、既使用量を引き継いだ新台帳を作る。確保区間の累積時間と現在のGPU期限を分け、再開で基準残高・予約数を戻さない。
2. GPUの実行ID・操作ID・資源ハッシュを取得から回収まで対応付ける。初発失敗と外側の失敗を分け、隔離wheelの一時領域を消す前に安全な診断を保存する。
3. 計画指示と変換を既知の反例で検証する。4Bに意味の誤りが残れば計画用9Bを限定比較し、採用候補を8題材で確認する。実際の入力と修正呼び出しも記録する。
4. 合格した実LLM計画を固定し、WAIの機能確認とKleinの作品確認へ進む。選択する瞬間と可視条件、編集元の用途を事前に確認し、編集後は場面全体を再評価する。
5. 累積検証とCIを確認し、停止・所有解放後に解決済みの新規一時データだけを整理する。

## 未達の扱い

人数・所有者・動作の不一致は、原文、計画、適用入力、実行グラフ、実画像の順に最初の差を特定する。再実行の成功や診断追加だけでは解決としない。過去の監視終了は原因未確定のまま保持し、最小再現と失敗注入で調べる。

保存済み17画像と元の評価は変更しない。WAIの機能確認へ照合済み計画を使っても、実LLMの成功や最終作品の合格には含めない。予算内で未確認の項目は反例、原因の確度、次に固定する条件を残す。
