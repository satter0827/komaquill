# 送信領域の再レビュー

対象: REQ-WEB-VISUAL-IDENTITY、REQ-CONVERSATION-ALBUM-UX、REQ-WEB-ACCESSIBILITY。

## 対象と方法

2026年11月5日、Windows 11、Python 3.12、Node 24、Chromiumで確認した。基準版は434557ce7a9829b108a8569b825e0ef698b82a65。以前の成功を引き継がず、要件、実画面、保存済みの記録、今回の実LLMの操作を照合した。公開API、保存形式、モデル、生成条件は変更していない。

画面、失敗した検査、各修正後の検査、実モデルの入力・応答・操作ID・使用量は`.artifacts/records/reports/cherry-zero-base-20261105`へ保持した。本文や画像を公開文書へ転載しない。

## 発見と修正

| 問題                                                           | 原因と修正                                                                                                     |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 高さ420pxの画面で行動追加後の発言欄が下へはみ出す              | 送信領域の内容が増えた分だけ領域全体が伸びていた。補助操作と発言フォームを分け、補助操作を標準スクロールにする |
| 文字200%で見出しが一文字に近い幅へ縮み、送信操作も画面外になる | 見出しの横並びと高さの制約が文字拡大を扱っていなかった。折り返しと縮小可能な領域を設ける                       |
| 文字200%でサイドバーが横へはみ出す                             | 固定px幅に文字だけが拡大していた。通常時の寸法を保ったままremへ変更し、名称の折り返しを許可する                |
| 補助操作を制限すると送信待ちの行動が隠れる                     | 描画設定より後ろへ行動の要約を置いていた。要約と確認事項を先に置き、発言に添える内容を優先する                 |

最初の修正案では送信欄が見出しや履歴を圧迫したため、その案を破棄した。次の修正で送信欄は収まったが行動の要約が隠れたため、配置を修正した。最終案では独自の位置計算を加えず、CSSと標準スクロールで役割を分けている。

Ubuntu CIでは、文字200%で行動を再追加する2件が失敗した。同じスクロール条件をWindowsでも高さ700pxで作り、日英・両密度の4件で再現した。補助操作のスクロール位置が追加前のまま残っていたため、行動の追加・更新時だけ先頭へ戻す。発言欄のフォーカスと履歴の位置は保つ。要約の表示条件を弱めず、CIの原ログと修正前の画面も保持している。

短い画面では返答がない会話にも末尾へ戻る操作が現れたため、保存済みの返答がある場合へ限定した。英語の接続エラーに残っていたストーリー生成向けの説明は、モデルの起動・接続と描画先への接続に絞り、日英の粒度を揃えた。

## 操作の確認

日英、通常・コンパクト、文字100%・200%、390×420・390×844・1440×960の組合せを回帰テストへ追加した。発言・送信の表示、横方向の収まり、行動の追加・取消・再追加・編集、Escape後のフォーカス復帰、下書き保持、一回の反映を確認した。修正前は4件失敗し、最終案で4件成功した。

実LLMは今回専用の作業フォルダーで、取得済み4Bモデルへ画面から3回送信した。すべて返答の保存まで完了した。待機行動は1件、経過時間は5分。途中でモデルとサーバーを停止し、非活性と下書き保持を確認した。同じアプリのプロセスを再起動せずにモデルを再起動し、明示的な次の送信が完了した。英語へ切り替えた後の返答は英語で生成され、保存済みの日本語の原文と人物名は保持された。画像生成とリモートGPU確保は行っていない。

これはUIと実モデルの結合確認であり、短い応答に不自然な敬語も観測した。長期の人物一貫性や会話品質全体の合格とは扱わず、保存済みの応答を編集しない。
