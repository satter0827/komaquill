# 検証手順

## 対応環境

開発環境はWindows x64またはARM64とPowerShell 7です。ARM64ではx64 Pythonを使用します。CIはWindowsとLinuxで実行します。Colabの検証GPUはT4です。モデルと生成セットは[既定設定](https://github.com/satter0827/komaquill/blob/91b503b1ee40a71506cc6c26fbf42e64a227651c/src/komaquill/resources/settings/defaults.toml)、Python、ComfyUI、フロントエンド、公式Colab CLIとGPU依存はパッケージ内の固定値と依存ロックに従います。

日本語の組版検査には、日本語の全使用文字を描けるフォントが必要です。Windows・LinuxのCIは、同じ固定版とSHA256を照合したNoto Sans JPを準備します。Linuxでは標準の利用者用フォントフォルダーを使います。取得元、照合値、取得時間の上限は[CI設定](../../.github/workflows/check.yml)を正本とします。フォント不足は組版失敗として扱い、文字を欠落させた出力や検査の省略で成功にしません。

外部ComfyUIには標準APIと、使用するモデル・標準ノードが必要です。モデル準備と素材保全にはKomaquillの画面拡張も必要です。

## GPUを使わない品質検査

開発環境を有効にして実行します。

```powershell
python scripts/check.py --level 2
```

選択したレベルの検査が終了コード0で完了することを確認します。既定はL2です。レベルは累積し、L3にはL1・L2のすべてを含みます。GPU確保や有料API呼び出しは行いません。

| レベル | 検査範囲 |
|---|---|
| L1：Static | 整形、lint、strict mypy、依存方向・循環参照、文書参照、作業ツリーの秘密情報・生成物混入 |
| L2：Test | L1に加え、Python・JavaScript・PowerShell検査、依存ロック照合、カバレッジ、実プロセスでのCLI基本操作 |
| L3：Full | L2に加え、隔離build、配布物検査、隔離wheelでのCLI基本操作、取得済みGit履歴全体の秘密情報 |

公開前とWindows／LinuxのCIはL3を実行します。`--plan --json`で検査ID、順序、前提と出力先を確認できます。`--check 検査ID`は前提工程を含む個別検査であり、全体成功として登録しません。

| 対象 | 確認内容 |
|---|---|
| Python | Ruffの整形・lint、strict mypy、依存方向と循環参照 |
| 生成と回収 | 送信前記録、受付不明の照合、部分保存、破損履歴、並行回収、重複防止 |
| 監視 | 親プロセス終了後の継続、二重起動、PID再利用、設定固定、起動中の停止 |
| 終了 | 通常・強制終了、切断後の復旧、ログ取得・GPU終了・後始末の個別結果、所有記録の保持 |
| モデル | 固定取得元とSHA256、同名別モデルのノード別対応、容量不足、取消、部分取得の再開、ローカル限定モデルの転送 |
| 素材 | 画像・マスク・Saveの観測、上書き前の版の保持、生成入力の固定、保存時の入力版の復元 |
| Windowsの保存 | 読み取り中の実ファイルとの共有競合、短時間の再試行、恒久的な失敗時の既存ファイル保持 |
| 画面拡張 | Node標準テストによる準備・取消・モデル参照の更新、配信ファイルと文言の同梱 |
| 評価 | 人・AIの識別、生成・画像参照、採否・選好、訂正の追記、JSONの一括登録・分析用出力 |
| 配布 | wheelとsdistの内容、隔離wheel環境での初期化・起動・生成・回収・停止、GPU転送物の展開とimport |
| 秘密情報 | Git履歴、追跡ファイル、設定、配布物への混入防止 |

カバレッジは未実行ファイルも含むsrc・scripts・bootstrapのPythonを対象にし、testsを除外します。行90%以上と分岐80%以上を別々に判定します。

結果は`.artifacts/records/reports/quality/実行ID/`へ保存します。`gate.json`に対象版、入力ハッシュ、工程ごとの開始・終了時刻、終了コード、失敗種別と未実行理由を記録します。失敗した工程の依存先を省略しても、独立した秘密情報検査は続けます。

`latest-attempt-lN.json`はレベルごとの最新実行、`latest-success-lN.json`はそのレベル全体の最新成功です。検査中に対象が変わった結果や個別検査は最新成功へ昇格させません。`--level N --status --json`で現在の入力との一致を確認できます。成功記録が存在しても、入力が変わっていれば現在の成功とは扱いません。

## T4と標準画面の検証

GPUを消費するため、品質ゲートとは分けて実施します。Google認証は起動端末で行います。作品・モデル・履歴を変更する前には、GPU停止、保存ファイルの一覧、SHA256を確認してください。

1. startで起動し、準備段階が進んで画面を開かずに端末へ戻ることを確認します。openまたはstart --openによる明示的な画面表示も確認します。起動コマンドの終了後もstatusが監視・GPU・接続を確認できることを確かめます。
2. CLI、App Mode、Node Graphから生成します。画像、実行グラフ、生成条件、実際のモデル・入力ハッシュ、画像の寸法とSHA256を照合します。
3. 不足モデルのある標準ワークフローを開きます。名前・容量・公開取得元・再利用対象を確認して準備します。確認前に取得が始まらず、準備後に不足表示が解消することを確かめます。
4. 標準の画像・マスクのアップロードとSaveを行い、同名の上書き前後を保存します。新しいランタイムで、保存時の入力版を参照するワークフローが復元されることを確かめます。
5. 監視とSSHを失った状態からstartで同じ所有GPUへ復旧します。モデルの全読み直しやGPUの追加確保がないことを確認します。
6. 通常終了で生成と保存を待つこと、強制終了で残った要求を回収不能として記録することを確認します。最終ログ、所有GPUの終了、監視・SSH・待ち受けの終了、再停止での追加確保がないことを確かめます。

再利用する検証コードはtests/liveに置きます。KOMAQUILL_LIVE=1とKOMAQUILL_PROJECT_DIRで対象を明示します。終了試験はKOMAQUILL_LIVE_STOPをnormalまたはrecovery-forceに設定して選択します。後者は検証対象の監視とSSHを中断してから所有GPUを停止します。業務中のセッションへ実行しないでください。

## ログと保存の確認

logs/ランタイムID/capture.jsonで、ログごとの取得結果と最終成功日時を確認します。shutdown.jsonは画像回収、素材保全、ログ、GPU、接続、履歴確定の結果を分けて記録します。失敗しても保存済みログを置き換えません。起動時と終了時の両方に問題がある場合は、元のエラーを表示し、終了側の結果をshutdown.jsonへ残します。

標準の画面拡張は.jsとして配信し、ComfyUIのキャッシュ抑制を使用します。GPU転送物に含むコードを、実際のComfyUI子プロセスの作業フォルダーからimportできることも確認します。

## 制約

新しいColabではモデルを取得し直します。同じランタイムへの再接続では準備済みモデルを再利用します。取得時間は配布元・ネットワーク・割当先に依存します。

認証が必要なモデル、取得元を確定できないモデル、追加ノード、動画・音声は自動導入しません。未保存の画面編集と拡張ノード独自のファイルは保全対象外です。PCの電源断やログアウト後のGPU終了は保証しません。

別のGPUサービスでの拡張利用は標準APIを境界とします。実際のGPU検証はColab T4で行い、他サービスの認証・割当・運用条件は個別に確認します。


## ストーリーの受入

日常ゲートではFakeListLLMと擬似ComfyUIで1・4・8枚、順次保存、部分失敗、二重実行、中断、再開、別条件での再生成を検査します。LLMアダプターの検査はlocalhostの擬似APIだけを使います。外部トレースの環境変数が有効でも送信しないこと、任意のキーや許可変数があっても日常ゲートから実モデルを呼ばないことを確認します。

実4Bの確認はKOMAQUILL_REAL_LLM=1、KOMAQUILL_PROJECT_DIRを明示し、tests/live/test_story_comparison.py::test_real_4b_fixed_and_autoを実行します。この入口は公開APIへallow_real_llmを渡し、複数の短い物語を固定4枚と自動枚数で比較します。結果は実行ごとに新しいフォルダーへ保全し、原文ハッシュ・条件・使用量・全呼び出し回数・所要時間を記録します。原文の出来事と結末、補足の区別は保存済みの計画を読んで確認します。

4場面の保存済み計画を用意してからT4を1セッション起動します。stories renderで生成し、全場面の完了前に最初の画像と本文を確認できることを確かめます。KOMAQUILL_STORY_RENDERに試行IDを指定したtests/live/test_story.py::test_real_story_saved_imagesで対応と実ファイルのハッシュを照合します。通常終了後にGPU・監視・SSH・待ち受けの終了を確認します。実機用の環境変数を日常の端末へ残さないでください。


## LLM効率化の検証

REQ-LLM-EFFICIENCYの機能検査は、固定入力と対にしたFake応答、localhostまたは通信モックの擬似API、保持済みの要求・応答を基本とします。入力に必要な情報が残ること、文脈予算、修正上限、言語違反、応答打ち切り、保存・再開を検査します。Fakeの結果で実モデルの理解力や文章品質が維持されたとは判断しません。

実LLMは擬似通信では判断できない互換性と品質の確認へ限定します。保存済みの証跡を先に確認し、変更の影響を受ける日英の短い会話、要約を要する会話、訂正、再開から必要な代表例を選びます。対象版、入力、モデル、生成条件、評価基準と呼び出し・出力・時間の上限を事前に固定し、操作ごとの明示許可を守ります。無関係な変更や同条件の再確認では実モデルを呼び直しません。

比較では、人物の役割、現在状態、所有関係、重要事項、生成言語、文章の自然さを確認し、入力・出力の総トークン量、呼び出し回数、待ち時間と別に判定します。要約・修正・下書き・画像用英訳の使用量も含め、一操作と会話全体を分けて記録します。概算、実測、不明値を区別し、固定の削減率を課しません。既知の未達、変更による品質の後退、失敗した要求も比較記録へ残します。

要約の記憶比較には、目的欄・現在状態・プリセットに答えが重複しない架空の入力を用意します。要約呼び出しを含む総量と、追加費用を回収できた範囲を記録します。個々の入力が短くなっただけで、会話全体の削減とは判断しません。仮説と終了条件を検証前に固定し、新しい仮説がない実モデルの再実行は行いません。

REQ-LLM-BOUNDARIESのSDK互換性は、正常・不正JSON、必須項目不足、余分な項目、言語違反、拒否、打ち切り、モデル不一致、通信失敗、使用量不明を通信モックと擬似HTTPで確認します。Fakeモデルの成功だけで構造化出力APIや提供元の例外処理を検証したとは扱いません。

比較・収集の証跡はproducerとreviewを分け、版・操作・用途・呼び出し順・モデル・指示・出力参照・使用量・評価者を対応付けます。元の生成物や評価は上書きせず、新しい集約出力と訂正から参照します。契約、集計、欠落・改変の検出、再開時の扱いはtestsで検査します。

## 保存済み画像の参照修復

REQ-CREATION-RECOVERYは実LLMとGPUを使わず、隔離SQLiteと架空の画像・操作記録で検証します。同じ対象・版・用途・描画入力に対応する一意の正常画像だけを候補とし、正常修復、競合、複数候補、入力不一致、編集・削除、欠落・破損、再実行を確認します。事前確認後の更新を上書きせず、操作完了と画像参照を同時に確定することを検査します。

実データへの適用は、使用中プロセスとDBの停止確認、整合したバックアップ、一覧とSHA256の記録、読み取り専用の候補確認を経て行います。通常の古い結果を適用しない条件は維持します。元の画像・Run・要求・評価と対象外の記録が不変であることを照合し、修復前後と保留理由を別の記録へ残します。

## 標準機能への委譲

[委譲計画](../plans/library-adoption.md)の機能は、対応する手書き処理の削除と製品固有の契約を合わせて検証します。候補の採否と検査範囲は[ADR 0015](../decisions/0015-library-delegation.md)、受入条件は要件台帳を参照してください。

| 要件 | 検証する内容 |
|---|---|
| REQ-SETTINGS-SOURCES | 明示入力・環境変数・作業設定・既定値の優先順位、空・偽・ゼロ、部分プロファイル、不正入力、作業フォルダーの分離、途中変更と再開 |
| REQ-API-QUERY-GENERATION | OpenAPIからの生成の再現性と型、取得・更新・無効化のkey、監視終了、受付不明、再マウント、遅れて届く応答、編集中の値と保存版の保持 |
| REQ-DOCUMENTATION-PARSING | 参照形式・括弧・エスケープ・日本語・画像・装飾付き見出し・Setext・重複見出し、コードの除外、欠落・作業領域外の参照、既存文書と要件の対応 |
| REQ-WEB-ACCESSIBILITY | 主要な操作状態の日英検査、axeの適用可能な違反と判定不能、キーボード、フォーカス、拡大、狭い画面、読み上げ名 |

設定と文書の検査は架空ファイル、画面の検査は隔離したPlaywrightと擬似APIを使います。生成物は一時領域へ作り、追跡中の生成クライアントとの差分を検査します。画面の再取得を生成開始や保存確定の代用にしません。axeの機械判定を操作や読み上げの全面的な適合確認へ広げず、判定不能と未実行を明示します。

保存・再開・競合の操作列は既存の隔離DBと擬似通信で検査します。Grimp、React Hook Form、Hypothesis、Linguaの導入を受入条件にしません。標準ASTによる選択の保守的な全件選択、元の履歴、操作ID、古い結果の適用防止を維持します。ライブラリ追加時は実行環境・開発環境・GPU転送物の依存を分けて検査します。

## テストの配置と公開API

単体はtests/unit、複数の境界を通す検査はtests/integration、依存・配布・入口の構造はtests/structure、隔離導入はtests/e2eへ置きます。各分類内は機能単位で整理します。tests/liveは既定のpytest実行とVS Codeの検出対象へ含めません。

隔離wheelではGitのない作業場所からClientとCLIを使い、本文・画像・履歴の対応を確認します。利用側コードのstrict mypy、py.typed、追加依存なしのimportとヘルプ、GPU用部分パッケージの単独importも検査します。importは通信・認証・ファイル作成・プロセス起動を行いません。


実4Bの比較記録は、成功と拒否の両方で作成します。件数、成功率、全呼び出しの使用量、成功した計画1件当たりの総量を分けます。途中で残せなかった計測値は不明とし、保存済み原本から観測を補う場合はその根拠を別に記載します。代表例を個別実行する場合はpytestの完全なnode IDを指定します。


## 候補バッチの実機測定

明示的に起動済みのT4と確認済みの4場面計画を使い、次を実行します。GPUを新規確保する処理は含みません。

```powershell
python -m tests.live.batch_acceptance --story-id STORY_ID --allow-gpu
```

ウォームアップ1枚、候補数1・2・4で各4枚、物語各2候補の8枚を生成します。続いてApp ModeとNode Graphから各2枚を生成し、通常のstopと提供元の停止を確認します。結果は非公開の.artifacts/records/reports/batch-candidatesへ保存します。

実行順とウォームアップ、保存観測の間隔、VRAMの観測範囲を結果に明記します。速度測定と画質比較を区別し、バッチで使われる乱数列から単画像のseedを推測しません。候補の評価には全候補不合格と判断保留を含めます。

Klein移行の短編完成検証は[専用手順](story-completion.md)を使います。以前のバッチ速度測定の出力予算と合算して実施せず、一つのT4セッション内でCLI・画面・編集と4場面の完成を検証します。
