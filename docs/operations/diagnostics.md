# 状態と保存を調べる

## 状態を切り分ける

同じ作業フォルダーで`komaquill status`、`komaquill doctor`、`komaquill logs`を実行します。statusは所有GPU・監視・接続・未保存を分けて表示し、doctorは利用する標準ノードとモデルを確認します。確認だけではGPUを確保しません。

記録を読めない場合は対象ファイルを保全し、JSONとアクセス権を確認します。所有記録は停止確認に必要なため削除しません。接続可能な結果は`collect`で回収し、所有GPUの終了には`stop`を使用します。

## ログの役割

| 記録 | 内容 | 判断できないこと |
|---|---|---|
| records/logs/cli.jsonl | 時刻・操作・状態変化・安全な失敗分類。監視操作IDと要求IDを区別 | 正常な全ポーリングの履歴 |
| ランタイム別captures.jsonl | ログ取得の試行とファイルごとの成否 | 取得できなかった内容 |
| ランタイム別capture.json | ファイルごとの取得成否・取得時刻・最終成功日時 | 取得に失敗したログの最新内容 |
| ランタイム別shutdown.json | 回収、素材、ログ、GPU、接続、履歴の個別結果 | 未確認のプロバイダー終了 |
| records/reports/quality/ID/gate.json | 検査入力、対象コード、各工程と全体の成否 | 別の版や現在の接続状態 |

以前のログは取得失敗時にも保持します。プロンプト全文、認証情報、応答本文、例外本文・変数は診断へ保存しません。プロンプトなど作品の再現条件はdata/runsに保存します。

## 検査環境で失敗する場合

Windowsのアプリ制御が新規仮想環境のpython.exeを拒否すると、隔離buildやwheel E2Eは失敗します。終了コードとOSイベントを確認し、管理者の運用方針に従って環境を整備してください。検査を省略して成功扱いにしたり、セキュリティ機能を自動無効化したりしません。

通常ゲートを実行できない環境で、既存環境による個別検査を行った場合は、その範囲と制約を記録します。CIの対象コミットと結果を照合し、ローカルで未実施の工程と区別します。


計画・生成・起動には固有の操作IDがあります。終了済みセッションのIDを無関係な計画へ継承しません。公式Colab CLIで失敗した場合は、工程・SDK版・例外種別・関数名を確認します。接続の準備待ちを行い、失敗時は接続を閉じます。例外本文を根拠なく推測したり、GPU再確保で回避したりしません。

ストーリーの本文やモデルの可視出力は作品内のplanningに保全します。診断ログへ転載しません。設定ファイルを変更しても、起動中の監視や進行中の表示追跡は確定した設定を使います。

GPUの取得イベントは実行ID・操作ID・資源のSHA256を記録します。GPU側のログ配置は回収契約を維持し、ローカルの実行別ディレクトリーへ回収します。初発の準備失敗を保持し、外側の失敗は直近の失敗として分けます。隔離wheelでは一時領域の削除前に許可した診断項目を検証レポートへ保存します。

Windowsでファイルの置換が拒否された場合は、初発のエラーコードと置換前後の状態を確認します。既知のアクセス・共有競合だけを短時間再試行し、未知の拒否や永続する失敗は成功へ変更しません。計画実測のチェックポイント、配布物、ログ回収、素材保全、移行は[共通の原子的保存](../../src/komaquill/infrastructure/atomic.py)を使います。検証用一時領域に確定前のファイルが残る場合は、削除前に最小限の証拠を保全します。
