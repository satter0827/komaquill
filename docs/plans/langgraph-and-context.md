# LLM処理・文脈管理・画像反映の改善計画

対象: REQ-LLM-BOUNDARIES、REQ-LLM-EFFICIENCY、REQ-CREATION-RECOVERY、REQ-CREATOR-ACCEPTANCE。

## 到達点

設定共有、共通LLM実行、文脈予算、LangMem、API取得の生成、文書解析、画面の機械検査は実装済みである。[現在の分担](../current/library-delegation.md)を正本とする。保存済み画像の参照復旧は公開APIとCLIへ実装し、停止・バックアップ後に実DBの1件を修復した。契約と操作は[画像参照の復旧](../current/image-recovery.md)を参照する。

指定チャットの変更を同じ作業フォルダーの差分と照合し、新ブランチへ集約する。旧roleplay-chatの構成を一括マージせず、既存ブラウザー、App Mode、Node Graph、単発画像生成を維持する。

## 実LLMの確認と採用条件

通常モデルは設定済み4B、日本語を既定とし、画像の基準はWAIとする。日常検査はFakeと擬似APIで行う。実モデルは入力・条件・モデル・対象コードを固定した日英の短い会話と、要約を伴う会話だけを比較する。上限は[scriptsの設定](../../scripts/llm-efficiency.toml)、収集は[比較処理](../../scripts/compare_llm.py)を正本とする。

入力JSONの圧縮とスキーマ注釈の削減は、使用量が減った例でも品質維持を確認できなかったため採用しない。元の入力形式と注釈を維持する。要約の出力言語を本文とtextフィールドへ明示し、言語不一致を型不正と区別して記録する。

人物の役割、現在状態、所有関係、生成言語、重要事項と自然さを、総使用量・呼び出し回数・待ち時間と分けて評価する。要約・修正・英訳を合計から除外せず、不明値をゼロとしない。限定した比較だけで品質維持や長期の削減効果を断定しない。

## 残る受入

REQ-LLM-EFFICIENCYは進行中とする。保存成功や実行完了を、意味の正しさと全体の効率化へ広げない。4Bの移動、所有関係、描写と状態の矛盾、文体の弱点は、保存した例と期待との差で管理する。WAIの年齢・性別・人物同一性は以前の実画像評価の課題として分ける。

新しい最適化は、失敗した条件と原本を残し、必要な情報を維持した同一入力比較で採否を決める。語句の置換や特定の発言への分岐で意味の誤りを隠さない。常時二段のLLM、モデルの自動切替、ベクトルDB、追加キャッシュ、汎用agentは導入しない。

## mainへの反映

新ブランチで関連差分と指定チャットの変更を確定し、要件、現在設計、テスト、操作手順、[検証結果](../verification/results/finish-library-and-llm.md)を同じPRへ揃える。変更中は関連検査、最終版ではcheck:ci、check:all、buildを実行する。PRの最新SHAでWindows・Linux、quality、securityの成功を確認する。

今回の明示依頼に限り、確認済みのPR先頭SHAを指定してマージする。未達の生成品質や効率化を達成済みとせず、マージ結果と残存課題を分けて報告する。
