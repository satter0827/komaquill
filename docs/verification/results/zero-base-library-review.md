# 会話開始・受付確認・保存の再レビュー

実施日: 2026年11月1日（日本時間）。基点はPR #38のマージコミットe20b19341892263d5edca0535cfbfb212610311b。「作る・保存する・選ぶ・会話する・現在の場面を描く・再開する」を基準に、要件、公開API、HTTP、React、保存と生成の境界、既存の実出力を確認した。

## 発見した問題と修正

### 受付応答が失われた後の復帰

サーバーが会話を受け付けても、POSTの応答だけが失われると、画面が操作状態を取得せず送信できなくなっていた。描画では取得済みの操作を受付結果へ反映せず、確認操作を終えるまで次の描画ができなかった。

同じ操作IDの取得を使い、受付済みと判明した結果を通常の受付と同じ経路へ反映する。TanStack Queryの通知を既存の操作監視で共有し、対象のQueryキーとIDを確認して一度だけ処理する。確認後のキャッシュ更新より前に通知の購読を終了し、再入を防ぐ。入力中の次の文章を保持し、取得だけでは要求を再送しない。

修正前は日英の実ブラウザー検査で、保存後の返答が表示されない問題を再現した。修正後は日英の会話、複数の描画、再読込、未到達の要求の明示的な再確認を検査した。新しい描画は別ID、同じ要求の再確認は同じIDであることも確認した。

### 直接入力で失われる開始場所と目的

プリセット経由だけが初期状態を設定し、公開Python APIとHTTPへ直接渡したscenarioのplace・goalは会話状態へ反映されていなかった。LLMへの文脈では、この2項目を現在状態から渡すため、直接入力の設定が失われていた。

会話開始の共通処理で、initial_stateで未指定のplace・goalをストーリーから補う。明示した値や空文字列を優先し、プリセット固有の重複した初期化を削除した。既存会話を再解釈せず、新規会話に解決済みの定義を保存する。

Python APIとHTTP、初期状態の省略・部分指定・明示的な空文字列、再起動後のリセットを検査した。修正前は6条件中4条件で開始場所が失われ、修正後は6条件すべて成功した。

### 回帰検査のキャッシュ更新先

状態編集の検査に、生成クライアントへ移行する前のQueryキーが残っていた。実際の会話キャッシュが更新されないため、編集中の入力と版の保持を十分に検査できていなかった。製品と同じ生成キーへ置き換え、関連する画面の検査を再実行した。

### 同じ文章を打ち直した場合の入力保持

全体検査が通った後の再レビューで、送信中に入力を消して同じ文章を打ち直すと、受付時に新しい入力まで消える問題を再現した。入力の保持を文字列の一致だけで判断していたことが原因である。送信時の編集回数と現在の編集回数を比較し、再入力した文章を保持する。元の要求を明示的に再確認するときも、再入力の情報を古い送信へ付け替えない。

異なる文章と同じ文章の両方をReactで検査し、受付応答が失われる日本語のブラウザー検査にも同じ文章の再入力を含めた。初回の全体検査と配布物は保持し、追加修正後の結果と区別する。

## 再レビューと検証の範囲

各修正後に、受付済み・未確認・拒否、操作ID、版、初期設定と現在状態、保存と画像生成の責務を再確認した。追加の回帰検査では、通知の再入、別のQueryや別IDの混入、未到達の要求の自動再送がないことを確認した。

関連するPython検査は97件成功した。最終差分のReact検査、画面の復帰検査、lint・formatter・型・全体テスト・配布検査と内容ハッシュは、非公開の.artifacts/records/reports/zero-base-library-e425c49183864866acd34c6f7efa2960/review-summary.jsonおよび参照する機械記録を正本とする。画面の証跡は実行ごとに画像・操作・通信・ハッシュを対応付けて保持する。

日常検査にはFakeとローカルの擬似APIを使用した。作品DB、モデル、元画像、過去の評価は変更していない。実LLMとGPUは追加で実行していない。
