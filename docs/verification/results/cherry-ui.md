実際のモデル呼び出しは7回で、英語の動作記述を修正する1回を含む。応答が記録した使用量は入力8,029、出力1,101、合計9,130トークンだった。計数用の読み取りは推論回数へ含めない。初回の4件の呼び出し記録はSHA256で照合し、後続の検証で変わっていないことを確認した。

実LLMを最後に確認した実行コードはca9081f。その後の変更は配色・テスト・文書であり、バックエンドの内容が同じであることを照合した。画像生成とリモートGPU確保は行っていない。起動したモデルをアンロードし、LM Studio APIの停止とポート解放を確認した。停止後も下書きを編集でき、送信が非活性になることを確認した。

この結果は短い会話とUIの結合確認であり、モデルの品質全体や長期の人物一貫性を保証しない。保存済みの日本語の情景は、表示言語の切替で翻訳せず保持した。

### 停止・再起動で追加確認した問題

追加の4回目の送信では、LM Studioを再起動した後にアプリ内の計数用WebSocketが古いまま残り、推論前に失敗した。送信内容は保存され、自動再送は起きなかった。長寿命のSDKクライアントとモデルハンドルを削除し、公開SDKの読み取りセッションを計数ごとに閉じる構成へ変更した。文脈上限も予算の作成時に読み直し、以前の予算を無効化するために別の操作の接続を閉じない。

SDKセッションの更新と文脈上限の変更を単体テストへ追加した。修正後はアプリを起動したまま実モデルを停止・再起動し、その後の新しい送信が完了した。失敗した操作には推論の記録がなく、自動再送されていないことも照合した。

### 検証記録の保存

全対象検査で、Windows上の検証記録の置換がEPERMで失敗した。読み取りハンドルが置換を一時的に妨げる条件で同じ失敗を再現した。実際にロックを保持していたプロセスは特定していない。一度だけのrenameをatomicallyの原子的保存へ置き換えた。ロック中は元のJSONを保ち、解除後に保存する回帰テストをWindowsで追加した。修正前の失敗と修正後12件の成功を別の記録へ保持した。
