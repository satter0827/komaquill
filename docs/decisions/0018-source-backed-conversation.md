# 原文を根拠にした会話と文脈管理

対象: REQ-CHAT-WORKFLOW、REQ-CHAT-MEMORY、REQ-LLM-EFFICIENCY、REQ-CHAT-CHECKPOINT。

## 背景

保存済みの実4B応答では、文脈に余裕がある場合も履歴の件数で要約し、合言葉や動作の特徴を失っていた。要約へ正しい内容を渡しても、返答で別の場所や意味を創作する例があった。JSON Schemaは構文を制約するため、項目の意味をスキーマの説明だけに置けない。

## 判断

公式SqliteSaverと操作IDによる永続化を維持する。通常応答は一度の生成を基本とし、本人の確認が必要な提案と、相手・環境の変更差分を分ける。人物と場所の確定値はアプリケーションが保持し、モデルに状態全体を再生成させない。状態を変えない身振りも本文とは別の動作として保持する。

事実回答専用のスキーマと原文参照IDの選択を試したが、訂正前の事項や質問と無関係な人物情報を選ぶため採用しない。出典が正しいことは、質問への回答が正しいことを保証しない。候補モデルへの既定の切替も行わない。

記憶は文脈予算を超える場合だけ作る。自由文の再要約を廃止し、原文の引用と出典を選ぶ有限処理へ置き換える。引用、話者、ターンの順序、消費済み範囲のハッシュを保存記録と照合する。必須入力と直近の完全な履歴を黙って切り捨てない。LangMemへの依存は削除する。

LM Studioの計数は公式SDKで読込済みモデルのテンプレートと文脈上限を使う。未ロードのモデルを自動起動しない。概算、送信前の計数、応答で得た使用量を区別する。構文制約のスキーマと実際の入力は別に予算化し、文字数の安全上限も維持する。

履歴は発言・台詞・環境・動作・確定済み行動を区別して投影する。同じ内容が連続するときは回数と位置を残して表し、状態やメモが異なる境界をまとめない。元の履歴と内容ハッシュは変更しない。必須入力と直近履歴だけでも予算を超える場合は、記憶作成の追加送信より先に停止する。

WAIの人物別領域指定も試したが、人物数、視点、年齢、髪や服の対応を満たさないため採用しない。モデル固有の品質指定と標準ワークフローの既定値を維持する。実験のソース、生成条件、失敗した出力を含む原本は非公開の検証記録へ残す。

## 保存と移行

旧要約を原本として退避し、新しい記憶は元の履歴から作る。移行では本文、ターン、画像、過去の内容ハッシュを書き換えない。停止、バックアップ、一覧とハッシュの照合は既存の明示的な移行処理で行う。

旧履歴には現在の型の既定値が含まれない場合がある。照合には保存されたJSONを使い、型の展開結果でハッシュを計算し直さない。記憶へ渡す範囲のハッシュも保存アダプターから取得し、LLM側に旧保存形式の再構築を持ち込まない。

## 検証

Fakeと擬似APIでは、原文にない引用、出典の改変、再起動、空の返答、移行時の原本保全を確認する。実LLMでは、合言葉、訂正、動作、行為者、現在の服装、未知の事項を日英で確認する。成功した応答だけでなく、修正、失敗、英訳を含めた全呼び出しと待ち時間を比較する。計数と保存の成功を文章品質の合格と扱わない。

今回の実機比較では意味の正確さを維持した総量削減を確認できなかった。REQ-LLM-EFFICIENCYは進行中とし、採用した文脈管理の仕組みと、未達の品質・効率の受入を分ける。結果は[会話とWAIの受入検証](../verification/results/llm-acceptance.md)を参照する。
