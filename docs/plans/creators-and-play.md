# 個人設定・キャラクター・ストーリーと会話体験

状態: 新規9要件の機能実装と実機確認を完了。自動検査の対象版・結果は検証記録を参照。現在の契約は [個人設定とプリセット](../current/creators.md) を参照。確認日: 2026-10-31 JST。

## 目的

物語の中の自分、相手となるキャラクター、舞台と導入を保存し、選んで会話を始められるようにする。作成画面を増やすだけでなく、作る・選ぶ・遊ぶ・続きを開くという流れで画面を再構成する。表示言語は日本語を既定とし、英語へ切り替えられるようにする。

固定サンプルを通常の動作確認の軸とし、ローカル4Bは明示指定時だけ使用する。固定サンプルは入力と対応する応答の組であり、任意の入力や翻訳を理解する実モデルとして扱わない。実モデルとGPUへの暗黙の切替・新規確保を行わない。

対象要件は要件台帳のREQ-PLAYER-PROFILE、REQ-APP-PREFERENCES、REQ-CHARACTER-PRESETS、REQ-STORY-PRESETS、REQ-PLAY-COMPOSITION、REQ-LOCALIZATION、REQ-IMAGE-TRANSLATION、REQ-ARTIFACT-LAYOUT、REQ-CREATOR-ACCEPTANCE。

今回の完成目標は、上記の新規要件をすべて達成することとする。個人設定、プリセットの作成と選択、画像、会話への反映、二言語対応、LLMの出力言語、画像用英訳、生成物の配置、実出力による検証を今回の対象に含める。後述の段階は実装順序であり、一部の機能だけで最終成果を完了としない。

精度の追求より、一連の操作が最後まで動く完成を優先する。初版はシンプルな機能と設計で全体を接続し、文章の洗練、演出の細かな調整、画像品質の高度化によって他の必須機能を後回しにしない。実出力の弱点は記録し、基本動作を成立させた後の改善へ分ける。

完成の受入では、画面・API・保存・生成が接続され、保存済みのプリセットから会話を始め、設定と言語が反映され、英語化した説明で画像を生成・保存・表示できることを確認する。設定の反映漏れ、言語切替の未達、英訳の未実施、未接続の操作、保存の失敗を精度上の問題として免除しない。固定サンプルの成功を実4Bや実画像の確認へ置き換えない。

現行の通常LLM要求はsystemメッセージを二つ作る。手元の4Bではその構成を受け付けず、検証用に一つへ統合すると構造化応答を取得できた。接続定義のモデルIDと手元の登録IDも一致していなかった。製品コードの修正は本計画の実装時に行い、実環境に合う明示的なプロファイルを設定する。

## 保存する情報

| 情報 | 主な内容 | 会話への適用 |
|---|---|---|
| 自分のプロフィール | 名前・呼ばれ方・外見・立場・紹介 | 選択した内容を会話の定義へ固定する。複数保存と既定の選択を扱う |
| 表示・生成の好み | 言語・文字の大きさ・表示密度・描写量・画像頻度・明示的に選ぶ接続先 | 表示設定は画面へ適用し、生成条件は操作の受付時に固定する |
| キャラクター | 名前・外見・性格・話し方・背景・自分との関係・代表画像 | IDと選択時の版、実際に使う内容を会話へ固定する |
| ストーリー | 題名・紹介・世界観・導入・最初の場面・当面の目的・登場人物・バナー | 長編を自動完結させる計画ではなく、会話で進む物語の開始設定として扱う |

保存内容はSQLite、画像とLLM入出力は.artifacts内のファイルへ保存する。画像の保存キー、用途、生成操作、元の設定の版を対応付ける。キャラクターとストーリーを同じ汎用JSON編集機構へ押し込めず、それぞれの型と検証を持たせる。

プリセットを編集しても、開始済みの会話の設定と履歴を遡って変えない。新しい会話では更新後を選べる。初版では既存会話への変更の自動追従を設けない。

## 作成と画像

手動入力と保存は実LLMなしでも利用できる。4Bによる作成補助は入力から下書きを作り、利用者が確認して保存する。モデルが利用者の指定を黙って補足・変更しないよう、指定内容と提案を区別する。

画像は設定を保存した後に独立した操作として生成する。接続済みで許可された生成先があれば、保存操作から代表画像・バナーの生成を開始する。接続がない場合も設定は保存し、画像が未生成であることと次の操作を示す。GPUを暗黙に確保しない。画像の失敗でプリセットや会話の保存成功を取り消さない。

キャラクターの代表画像、ストーリーのバナー、会話中の場面画像を区別する。初版は用途ごと一枚とし、生成中は採用済み画像を維持する。バナー画像へ題名を描かせず、文字はReactで重ねる。横長のバナーと人物画像では構図・切抜き位置・生成条件を分け、実際の表示サイズで確認する。

現在の標準WAIは文章からの生成が中心であり、同じ外見の説明を渡しても別画像で同一人物になる保証はない。外見設定の維持と、顔の同一性の評価は分ける。参照画像を使う場合は生成セットの対応能力を確認し、未対応の独自ノードを追加しない。

## 言語と画像用の英訳

- 初回は日本語。利用者の言語選択を保存し、再起動後も維持する。英語版の操作・案内・失敗説明は英語に統一する。
- 日本語版は操作を日本語で明確にし、短い英語の見出しを補助的に使う。全操作を二言語併記にして画面を混雑させない。日本語の長さ・改行・字体に合わせて設計する。
- 表示言語に合わせ、LLMが生成する会話・キャラクターやストーリーの文章も切り替える。保存済み本文や固有名は自動翻訳しない。
- 言語は各操作の受付時に確定する。処理中の切替や同じ操作IDでの再確認によって要求の言語を変えない。
- 「入力言語を維持する」指示と表示言語の指示を併存させず、有効な出力言語を一つにする。日本語入力・英語表示、日本語の履歴・英語への切替も実LLMで確認する。
- 画像へ渡す説明は表示言語にかかわらず英語にする。日本語の原文、英語の説明、翻訳に使ったモデル・指示、適用済みの品質条件、実行グラフを対応付ける。
- 会話画像は会話の一回の構造化応答内で、表示用本文と英語の画像説明を分ける。手動の日本語画像説明も英語化してから送信する。入力が英語なら不要な再翻訳を避ける。
- 固定サンプルの英訳は対応する入力の組だけを使う。任意の日本語の英訳には4Bの明示利用を必要とし、未許可・失敗なら画像送信前に停止する。再開では保存済みの英語入力を使う。

表示文言は言語別のカタログへ集約し、エラーコードと表示を分ける。日付・数値は標準の国際化機能を使う。開発ログ・識別子・コードは英語を維持し、利用者データを機械的に翻訳しない。実装時に現在の英語表示に関する規約とカタログの構造を更新する。

## 画面と文言

主な入口を「遊ぶ」「キャラクター」「ストーリー」「あなた」とし、表示・生成の好みと接続の詳細は設定へまとめる。ホームでは続きの物語と保存済みのストーリーを見せる。初回の操作は、自分と登場人物を選び、物語を始める流れに絞る。

会話作成は、すでに保存した自分・キャラクター・ストーリーのプリセットを選ぶ画面にする。名前・概要・代表画像やバナーを見て選び、開始する内容を確認できるようにする。設定本文を毎回入力するフォームは基本の導線に置かない。プリセットがない場合は該当する管理画面へ案内し、保存後に会話作成へ戻って選べるようにする。

キャラクター・ストーリーの作成時は画像プレビューと短い基本項目を並べ、詳細は後から開く。会話中は本文を中央、人物画像と要点を補助位置へ置く。バナーは開始時に見せ、会話中は小さな見出しへ収める。狭い画面では会話を優先して補助情報を開閉する。毎発言の大画像や背景の連続アニメーションを既定にしない。

「システムプロンプト」「状態JSON」「Revision」などは通常の遊ぶ画面へ出さず、「話し方」「今の状況」「持ちもの」など操作対象に対応する表現へ変える。固定サンプルや実モデルを選ぶ案内は、実際の動作が分かる範囲で明示する。保存完了前の完了表示や仮の成功応答を演出に使わない。

操作部品のキーボード操作、フォーカス、画像の代替説明、文字と背景のコントラスト、拡大時と狭い画面の再配置を確認する。現状の二画面のスクリーンショットだけでアクセシビリティの適合を判断しない。

## バックエンドとフロントエンド

Pythonはプリセット・個人設定・会話の保存、版と操作ID、設定の合成、言語、LLMの構造化契約、英訳、画像生成の順序と状態を管理する。CLIとHTTPも同じ公開Python APIを呼ぶ。画像説明の翻訳やプロンプトの組立てをReactへ置かない。

Reactは入力とプレビュー、選択、ナビゲーション、言語別文言、配置と進捗を扱う。APIの型はOpenAPIから生成する。保存状態の正本や外部モデルの呼出しをブラウザーに重複実装しない。

現在のReact・Vite・Router・TanStack Query・Base UIの構成を利用し、必要な機能境界を整理する。画面の再設計をフレームワーク全面交換や汎用ワークフローエンジンの追加へ広げない。

## 生成物の配置

以下の用途で.artifactsへ集約する。既存のdataとrecordsは保全し、環境・キャッシュ・一時物の整理と混在させない。

| 保存先 | 内容 |
|---|---|
| .artifacts/runtime | Python・Nodeの導入済み環境、ブラウザー、実行に必要な依存実体 |
| .artifacts/cache | pnpm・Vite・Nx・型検査・依存検査等の再生成可能なキャッシュ |
| .artifacts/build | React出力とPython配布用の組立て |
| .artifacts/dist | wheel・sdist等の配布物 |
| .artifacts/data | DB・入力素材・画像・LLMの作品データ |
| .artifacts/records | 履歴・診断・検証記録 |
| .artifacts/tmp | 途中ファイルと検証用の一時作業 |

package.json、ロックファイル、Nx・Viteの宣言設定はソース管理する正本として残す。OpenAPIから作るクライアントも、配布するソースとして差分を検査する対象と、ビルド途中の成果物を区別する。

node_modulesはNodeの標準モジュール解決とpnpmのリンク構成を確認して配置する。実体を.artifactsへ置き、標準パスに参照が必要なら最小限のリンクだけを残す方式を先に検証する。単に移動してimport解決を壊さず、ルートを完全に無くすためだけの独自ローダーを追加しない。

既存の.nxと.import_linter_cacheは残存物か再出力かを計測して切り分ける。導入・起動・lint・型検査・テスト・ビルド・配布・CIの全経路で出力先をそろえる。移動前に利用中プロセス、対象一覧とハッシュ、最終絶対パスを確認し、移動後に照合する。ユーザー領域の認証情報は移動しない。

## 調査時の実LLM確認と懸念

手元のローカル4Bを検証用にロードし、既存の作品と設定とは別の作業場所で確認した。製品経由の要求二件はHTTP 400に起因する失敗として保持した。製品ソースを変えずにメッセージ構成を変更した比較ではJSONを取得できた。これは製品経路の修正完了ではない。

日本語の応答では名前・所持品・舞台の一部が反映された一方、呼ぶ側と呼ばれる側の取り違え、指定のない施設設定、情報をそのまま読み上げる不自然さがあった。日本語の場面説明には人物名しかなく、外見を自己完結的に含まない例もあった。JSON検証だけで自然さ・同一性・設定の意味的一致を合格にしない。

英語指定を追加するだけの比較では日本語の応答が残った。入力言語を維持する指示との競合を除く比較でも日本語のままであり、英語出力は未達だった。両方の失敗結果を保持する。二言語・表示切替・画像用英語は異なる受入条件として検査する。

入力、可視出力、使用量、処理時間、比較条件、画面は.artifacts/records/reports/creator-research-20261031へ保持する。画像生成・T4・人物画像やバナーの画質は本調査では確認していない。

## 実装と受入の順序

1. 実モデルの接続ID・メッセージ契約・安全な失敗分類と、生成物の出力経路を確定する。
2. 個人設定・言語・キャラクター・ストーリーの保存APIを実装し、再起動・編集・削除・既存会話への非追従を確認する。
3. 保存済みの自分・キャラクター・ストーリーを選んで会話を作る導線と、未作成時の管理画面への往復を実装する。選んだ設定を開始時に固定し、固定サンプルと明示した4Bの実行を分ける。
4. 代表画像・バナー・場面の英語化と生成・再生成・保存・画面への反映を通す。
5. 二言語の画面とゲームとしての導線を実装し、実4Bの本文と保存状態、実際の画像を見て受入する。

変更中は関連する検査を選び、節目で全体検証と配布を確認する。受入には日本語・英語、会話途中の言語切替、異なる世界観、他のプリセットとの混線、画像失敗、途中終了、要求再確認、キャッシュなしの初回実行と再実行を含める。実LLMと実GPUは日常ゲートへ混ぜない。
